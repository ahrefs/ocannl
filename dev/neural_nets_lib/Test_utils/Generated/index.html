Module Test_utils.Generated

Freshness-checked reads of the generated kernels under build_files/, for tests that assert on emitted code. Artifacts outlive the run that wrote them, so a read that does not establish provenance can keep asserting on a kernel that is no longer emitted at all.

Freshness-checked reads of the generated-kernel artifacts under build_files/ (gh-ocannl-655).

Tests that assert on emitted code read build_files/<exe>/<routine>.<ext>. The artifact is a side effect of a compile, not a value the test holds, and nothing in the path ties it to the compile it is supposed to describe:

  • test/config/ocannl_config sets clean_up_build_files_on_startup=false, so an artifact outlives the run that produced it, indefinitely. A test asserting "the kernel contains single_to_fp8" keeps passing after the kernel stops being emitted at all -- folded to a constant, erased by precision inference, fissioned into a differently-named routine -- because it is reading the previous run's file. A structural check that has quietly stopped structurally checking is worth less than no check, because it is counted as coverage.
  • Within one run, two compiles under the same routine name overwrite each other's artifact. A loop that compiles several candidates under one name and credits each with what it finds on disk afterwards is crediting candidate N with candidate N-1's source whenever a compile skips emission (a schedule-cache hit, a reused artifact, a conditional write).

So this module owns the read, and makes both cases fail rather than pass:

  • init -- called once, before any compile -- empties this process's own build_files/<exe>/ subdirectory. Every artifact present afterwards was written by this run, so existence *is* freshness and no clock is involved. What makes that safe is that the DEFAULT subdirectory is derived from the executable's own name and dune runs one process per executable, so nothing else writes there. The other two resolutions are not this process's to empty and get their own treatment: any configured build_files_prefix, flat or named, is refused, because that directory is not this process's to empty (a second executable can be given the same prefix) and without deletion nothing distinguishes a re-emitted identical kernel from a stale one -- deletion is the only write signal independent of timestamp granularity.
  • read fails the run (through Verdict, so the exit status carries it and no dune promote can bless it) when the artifact is missing. Silence must not be indistinguishable from a pass, which is what a string option returning None invited: some call sites recorded that as false, others forgot it.
  • Reading one routine twice, with the artifact's contents having changed in between, is reported as an overwrite: within a run that is a same-named second routine, or an unarmed second candidate. arm -- delete this routine's artifact, right before compiling the candidate that should produce it -- is how a loop says the overwrite is intended, and turns "was it really candidate N's kernel?" into a checked fact for each candidate in turn.

A test whose leg the backend cannot evaluate (a GPU intrinsic on a CPU backend) must not reach read at all: gate the leg and report it with Verdict.skipped. An absent artifact is a failure here, deliberately.

init ~backend_name empties this executable's build_files/ subdirectory, so that every artifact found later was emitted by this run. Call it once at the top of the test, before any compile -- Verdict.fails if a read happens without it.

~backend_name selects the source extension (extension_of_backend; a name that is no backend's aborts the run here); tests already derive it as String.lowercase (Utils.get_global_arg ~arg_name:"backend" ~default:""). val arm : ?ext:??? -> Base.String.t -> Base.unit

arm ?ext routine deletes routine's artifact, so that the next read of it sees only what the *next* compile emits. Use it in a loop that compiles several candidates under one routine name: without it, the second read of a changed artifact is reported as an unattributed overwrite.

val read : ?ext:??? -> Base.String.t -> Base.string

read ?ext routine is the generated source routine's compile emitted during this run.

Fails the run, and answers "", when the artifact is missing: the kernel was not emitted, the routine is named something else now, or the test forgot Utils.settings.output_debug_files_in_build_directory <- true. Answering rather than raising keeps the run's remaining checks reporting; the failure is already recorded, so the exit status holds whatever the caller concludes from the empty source.

val kept_libraries : ?owner:??? -> Base.String.t -> string Base.List.t

kept_libraries ?owner routine lists the paths of the libraries kept for routine under output_dlls_in_build_directory (gh-ocannl-1247) or output_debug_files_in_build_directory (gh-ocannl-1335), in owner then compile order: those of this process (`This_process, the default), of the process with OS id p (`Pid p), or of every process (`Any). Names are read with the backend's own Utils.parse_kept_library_name, and the kernel name they carry is Utils.library_kernel_name's, so neither a renaming nor a routine name too long to carry whole can leave this listing looking for the wrong ones. A child process of this executable writes into the same directory, which is how a test sees another process's libraries; it must not call init itself, or it would sweep the parent's.

Like read, it answers from this run only: init emptied the directory first. An empty list is an answer here, not a failure, so a caller states the count it expects.

val main_logic_lines : Base.String.t -> Base__Int.t Base.List.t

main_logic_lines source is the 1-based numbers of the lines of a generated source that hold its kernels' statements, in program order: each kernel's lines after its Ir.C_syntax.main_logic_marker, up to the closing brace of its definition -- with, where the kernel was rendered OUTLINED (gh-ocannl-1603), each call to one of its parts replaced by that part's body lines. So a reading of a kernel's statements does not depend on whether a size threshold moved them into parts: the parts are found from what the renderer emitted -- the definitions carrying Ir.Kernel_outline.part_attribute, and the calls the main logic makes to them -- not from how they are named. The kernel's signature, its local declarations and the prepended builtins are none of these lines.

A source with no marker, a marker outside any definition, or a part definition no kernel's main logic calls (a reading that would silently miss its statements) fails the run through Verdict. The empty source -- what read answers after already failing -- reads as no lines.

Declared identifiers (gh-ocannl-2102)

Every identifier a generated source's kernels DECLARE, read off the text, so a test can hold the names the renderer mints against the rules that keep a node label from shadowing them.

What is read: each kernel's signature (its parameters), its body ahead of its Ir.C_syntax.main_logic_marker (function scope) and its statements (main_logic_lines, an outlined kernel's parts spliced in at their calls), and the body of every function-like macro the source #defines that a kernel statement calls (a macro body can declare: the register tile's bf16 row widening declares its dst argument). What is deliberately not read: the prepended builtins outside every kernel -- their functions' locals are another function's -- whose typedef names are read only as TYPE names; an outlined part's own signature (it re-binds names its kernel declares); comments, string and character literals; the preprocessor conditionals #if / #ifdef / #ifndef / #elif / #else / #endif and #pragma, whose lines are skipped, so BOTH arms of a conditional are read and every macro definition under them counts.

The reading is a fail-closed allowlist. A statement that starts with a declaration specifier (a C type or qualifier, __attribute__((...)), __typeof__(...), typedef, or a name the source typedefs), or with an identifier followed by a declarator (an unknown type name: in C nothing else starts a statement so), must take one of these forms, or it is declarations.unrecognized:

  • <specifiers> <declarator>; and <specifiers> <declarator> = <initializer>;, one declarator, where a declarator is *s (each optionally followed by const / restrict / volatile / __restrict), the identifier, [<digits>] subscripts and trailing __attribute__((...))s;
  • typedef <specifiers> <declarator>;;
  • a for header's first clause in either variable form, the loop's body read as a statement;
  • a signature parameter: <specifiers> <declarator>, no initializer;
  • a statement-level call of a macro the source defines, <macro>(<args>);: what each of its definitions declares (read by these same rules, the macro's parameters admitted as type names), the arguments its declared parameters receive among them, each a bare identifier;
  • a block literal inside an expression statement, ^(<params>) { ... } or ^{ ... } (the dispatch_apply rendering of a pool-parallel Grid loop passes its chunk body as one): each parameter in the signature-parameter form, the body read as statements.

Also unrecognized, as a declaration this reading cannot classify: a second declarator; a function declaration; struct / union / enum; a GNU statement expression ({ ... }); a label, goto, case or default; a call of a declaring macro anywhere but as a whole statement, a declared argument that is not a bare identifier, and a macro whose body pastes or stringifies (#, ##) or holds a statement these rules refuse; any other preprocessor directive in a kernel (#define there declares a macro). Everything else -- an expression statement, a call, if / else / while / do / switch heads (their bodies read as statements), return / break / continue, braces -- declares nothing.
