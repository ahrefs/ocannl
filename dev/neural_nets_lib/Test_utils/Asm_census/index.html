Module Test_utils.Asm_census

The -march compile matrix and the innermost-loop instruction census (gh-ocannl-650): compiling an emitted kernel under a target the build host cannot run is what makes a guarded arm checkable at all, and counting its innermost loop is what separates "gcc accepted the arm" from "gcc kept it in registers as one vector operation".

Static census of a generated kernel's innermost loops, and the -march compile matrix that feeds it (gh-ocannl-650).

Two questions about an emitted kernel are answerable without owning the hardware it targets, and neither was answerable by anything in the repository until this module:

  • does the guarded arm even compile where its guard is true? Every #elif for a foreign target (C_syntax.vec_fma_builtin's AVX-512, AVX512-FP16 and NEON rows) is emitted unconditionally and preprocessed away on the build host, so a syntax error, a wrong arity or a type mismatch inside one ships silently. gh-ocannl-621 caught exactly that -- gcc's aarch64 fp16 vector builtin is typed in __fp16, not the _Float16 the emission carries -- by compiling build_files/*.c under seven -march flags in a scratch directory that died with the session.
  • does it compile WELL? The same sweep was gh-ocannl-621's actual measurement: instructions, vector and scalar arithmetic, and stack references in the innermost loop that carries the accumulator update. That is a compile-time property, so it needs no hardware either, and it is what separates "gcc accepted the arm" from "gcc kept it in registers as one vector operation".

The two false readings this module is shaped around

Re-deriving the census by hand cost gh-ocannl-621 three iterations and two wrong answers, both of which a naive implementation reproduces:

  • selecting an outer loop. A reduction kernel nests: the accumulator update sits in the innermost loop, and counting an enclosing one dilutes every ratio. census therefore selects the smallest-span loop whose body carries the construct being censused, and it identifies that construct through DWARF line numbers (-g puts .loc directives in the assembly) rather than by guessing from the instruction mix. census_in's explicit outer-carrier selector is the narrow exception for a construct with its own nested codec loop. The caller supplies the source-line set; a loop is a candidate only if its body's .loc set meets it.
  • counting only the instructions the good outcome produces. Scoring vector FMAs alone makes a fully scalarized loop read as "no FMA loop found" -- a pass, from the failure. So the counts are separated (counts.vector_ops against counts.scalar_fp_ops against counts.libm_calls) and the SELECTION never consults them: it is anchored on the source, so a loop whose combine compiled to nothing but library calls is still found and still censused. census answering None means the anchor was not reached at all, which callers report as a failure rather than as an absence of findings.

What the counts mean

Classification is by mnemonic, from GCC/GAS and Clang assembly output for x86-64 and aarch64:

  • vector_ops: packed-SIMD instructions -- an x86 mnemonic ending in ps/pd/ph, a packed integer mnemonic, an operand naming %ymm/%zmm, an aarch64 operand in vector-lane form (v0.2d, q0), or an aarch64 mnemonic carrying the arrangement instead (fmla.4s), which is how Apple's assembler spells the same instruction.
  • scalar_fp_ops: an x86 mnemonic ending in ss/sd/sh other than a move from memory (a load, whatever its width), or an aarch64 f... instruction on a scalar FP register. This is the count that gives away SLP scalarization, which leaves no stack traffic behind.
  • libm_calls: a call to the censused class's library function (fmax/fmin and friends, fma/fmaf). One of these inside a vector loop is the worst outcome of all: an opaque call cannot be vectorized at any optimization level or grid size.
  • vector_fma_ops: the subset of vector_ops that are fused multiply-adds -- an x86 vfmadd/vfmsub/vfnmadd/vfnmsub family mnemonic on packed operands, an aarch64 fmla or fmls in either dialect's vector form, lane-indexed (v2.s[0]) included. It is what says an accumulator update stayed ONE vector operation: a register-tiled k-step issues exactly one per C-tile register, and a per-lane rendering of the same update issues none (gh-ocannl-948).
  • vector_fma_bytes: those FMAs' register widths, summed (%xmm/%ymm/%zmm = 16/32/64; an aarch64 arrangement's 8 or 16; 0 for a width no operand states). Against vector_fma_ops this tells a whole-width update from one the compiler SPLIT: clang on -march=x86-64-v4 prefers 256-bit vectors and legalizes a 64-byte GNU C vector as two ymm halves -- twice the FMAs, the count of a loop unrolled by two, at half the width each.
  • stack_refs: instructions addressing through the stack or frame pointer -- the spill signal gh-ocannl-614 measured. %rbp is a frame pointer only in a function that made it one (frame_pointer_lines); elsewhere both compilers allocate it as an ordinary register.
  • stack_writes: of those, the ones that WRITE the stack. A value round-tripping through a stack slot begins with one, where a reload of a spilled loop invariant does not (gh-ocannl-1102).
  • residual: instructions matched by none of those classifiers. Loop-control and integer bookkeeping legitimately live there, so it is reported rather than bounded; its purpose is to make a newly encountered dialect visible instead of silently returning zeroes. Stderr profiles show the eight most frequent residual mnemonics, with spelling breaking frequency ties and other counting remaining instructions (gh-ocannl-924).

Both aarch64 spellings are read, because both are compiled in CI and a dialect must not change the reading: a count is a fact about the instruction, and the same loop assembled two ways has to census the same. Both are exercised in test/operations/asm_census_cases's pure dialect probes.

Moves are the fuzzy edge (an %xmm operand does not by itself say whether a movq moved a lane or a vector), so the mnemonic rule below is deliberately narrow and the counts are reported as a profile rather than compared against fitted thresholds. Every claim built on them is an inequality that a wrong classification of a move cannot flip.

defines t is the set of preprocessor macro NAMES this toolchain predefines for its target.

This is how a column whose ISA its label does not spell out -- the host's own default target, which is whatever machine the run landed on -- can still be held to an ISA-scoped claim: the compiler is asked what it targets, instead of a hard-coded table asserting what a -march string implies. It answers for the named columns too, which is strictly better than the table was: -march=x86-64-v3 implying __FMA__ is gcc's fact to state, not this module's.

val compile : toolchain -> opt_level:int -> src_path:string -> asm_path:string -> (unit, Base.string) Base.result

compile t ~opt_level ~src_path ~asm_path compiles src_path to assembly, with -g so that census can anchor on source lines. Error output carries the compiler's diagnostics.

Assembly rather than an object file: -S runs the whole front end and code generator, which is everything a generated kernel can trip, and it produces the census input in the same invocation.

Source anchoring

val anchor_lines : source:Base.String.t -> patterns:Base.String.t Base.List.t -> (Base.Int.t, Base.Int.comparator_witness) Base.Set.t

anchor_lines ~source ~patterns is the set of 1-based line numbers of source containing any of patterns. This is how a caller names the construct to census -- the accumulator combine, the FMA update -- without depending on which preprocessor arm the target selected: list a substring of every arm and the one that survived is the one whose lines the assembly mentions.

val anchor_block_lines : source:Base.String.t -> within:(Base__Int.t, 'a) Base.Set.t -> patterns:Base.String.t Base.List.t -> (Base.Int.t, Base.Int.comparator_witness) Base.Set.t

anchor_block_lines ~source ~within ~patterns is the smallest brace-delimited source range containing every line of within (1-based line numbers) that holds one of patterns. The generated-kernel census passes the kernel's statement lines (Generated.main_logic_lines: after its main-logic marker, an outlined kernel's parts included), and uses a range rather than only the exact matching lines because clang may attribute an inlined conversion to another line of the construct. Braces in comments and literals are ignored (Generated.brace_intervals), so prose or macro strings cannot silently widen the range.

An empty within, an absent anchor, or unbalanced enclosing block returns the empty set. Callers already treat an empty anchor as a failed census rather than guessing at a wider range.

The census itself

val source_file_numbers : line option Base.List.t -> basename:Base.String.t -> (Base.Int.t, Base.Int.comparator_witness) Base.Set.t
val classify_asm : Base.String.t -> line option Base.Array.t
val frame_pointer_lines : line option Base.Array.t -> bool Base.Array.t

frame_pointer_lines lines is, per line, whether %rbp is the frame pointer there: from the prologue step that makes it one to the end of that function, as its unwind directives delimit it (.cfi_startproc/.cfi_endproc, and mingw's .seh_proc/.seh_endproc). A function keeps a frame to realign its stack for 64-byte spills, say, and sets it up by any of: movq %rsp, %rbp; an offset one, leaq 128(%rsp), %rbp (clang for mingw); and the unwind directive that records either, .cfi_def_cfa_register %rbp (or DWARF register 6) or .seh_setframe %rbp, N -- any one suffices, since a form this misses hides the function's spills. A listing without function delimiters keeps the frame from the first such line on, which errs toward counting.

One assembly file, classified once.

Everything below the line classification -- the loop edges, and the DWARF file numbers standing for the kernel's own source -- is a property of the FILE, not of the construct being censused, while a run asks about several dozen constructs per file. Parsing per question made the driver re-scan every one of a 40000-line listing's lines once per anchor, which was the larger half of test/operations/cc_march_census's wall clock once gh-ocannl-752 raised the loop count. Hence the split: parse once per compiled file, census_in once per anchor.

edge_count p is how many loop edges the branch vocabulary recognized in p at all, which is what separates the two readings of a census_in answering None: this construct was hoisted or folded away (some other loop was still found), or is_branch does not know this ISA's spelling and no loop in the file was found. The second is a defect in this module and reports every anchor missing at once, so it is worth a claim of its own.

profile_all op_class ~asm is the instruction profile of an ENTIRE listing, with no loop selection and no source anchoring.

For a listing that is one small function, which is what a toolchain PROBE compiles: the question there is what the compiler made of one expression, and there is no enclosing loop to find. A census of a generated kernel wants census_in instead -- counting a whole kernel would average every loop in it together.

type selection =
  1. | Innermost
  2. | Smallest_outer_anchor_carrier
val census_in : ?selection:??? -> parsed -> op_class -> anchor:(Base.Int.t, 'a) Base.Set.t -> t Base.Option.t

census_in p op_class ~anchor is a loop of p whose body carries a source line in anchor, with that loop's instruction profile. Innermost, the default, selects the smallest span. Smallest_outer_anchor_carrier takes the smallest candidate that contains another anchor-carrying candidate. The latter reads a vector reduction's immediate accumulator loop rather than either its per-lane codec or a more distant compiler loop that happens to share source attribution. If no nested pair exists it falls back to the ordinary candidates.

None means no loop carried the anchor -- the construct was hoisted, folded away, or never emitted. That is a finding, not an absence of one: report it as a failure.

val census_source_in : ?selection:??? -> parsed -> op_class -> source:Base.String.t -> patterns:Base.String.t Base.List.t -> within:(Base__Int.t, 'a) Base.Set.t -> t Base.Option.t

Prefer exact source anchors; only when none carries a loop, try the smallest enclosing construct of the within lines (anchor_block_lines). Trying the range eagerly can select unrelated compiler loops nested beside the accumulator (gh-ocannl-844). Shared by the real census and its pure controls.

val attributed_in : parsed -> op_class -> anchor:(Base.Int.t, 'a) Base.Set.t -> counts

attributed_in p op_class ~anchor is the profile of every instruction p attributes to a source line in anchor, in a loop or not: the reading for a construct that is not a loop of its own, such as the load of a register tile's C-tile before its k-loop and the store after it. An instruction belongs to the line of the last .loc above it, as in the DWARF line table. instructions = 0 means no instruction was attributed to the lines at all.

val is_conditional_branch : mnemonic:Base.String.t -> Base.bool

Whether a branch mnemonic is CONDITIONAL: is_branch less the unconditional jumps (b, jmp, jmpq).

val is_counter_test : mnemonic:string -> rest:Base.String.t -> Base.bool

Whether an instruction compares an INTEGER register with an immediate (cmpl $3, %r14d on x86, cmp w3, #3 on AArch64): the shape of a loop's control testing its counter against a constant bound, as unrolled and peeled loops do. A select over float data never compiles to it -- its test is a floating-point compare, or a test of a boolean computed from one.

val conditional_branch_sites : parsed -> anchor:(Base.Int.t, 'a) Base.Set.t -> branch_site Base.List.t * int

conditional_branch_sites p ~anchor is (sites, instructions): every conditional branch p attributes to a source line in anchor, in listing order, and how many instructions it attributes there at all -- attribution as in attributed_in, by the last .loc above an instruction. conditional_branches_in is its count.

val conditional_branches_in : parsed -> anchor:(Base.Int.t, 'a) Base.Set.t -> Base__Int.t * int * int

conditional_branches_in p ~anchor is (branches, counter_tests, instructions): how many conditional branch instructions p attributes to a source line in anchor, how many further ones it attributes there that test a loop counter, and how many instructions it attributes there at all (conditional_branch_sites, counted). The question it answers is whether a construct COMPILED to a branch (gh-ocannl-1622: a value select whose arm holds a load), which a loop census cannot tell from the loop's own control; the instruction count is there so that a construct the compiler folded away, or an anchor naming nothing, reads as 0 instructions rather than as a branch-free success.

A branch whose flags come from the instruction right before it, with no label between, and that instruction is is_counter_test, is counted apart (gh-ocannl-1660): DWARF attribution puts a loop's control on whatever line the compiler last stepped through, and gcc 13 attributed a peeled outer loop's cmpl $1, %r14d; jg to a select's line. It reads line-shaped forms only: a loop control with a register bound counts as a branch (a false red, never a false green).

val branch_site_to_line : ?source:??? -> branch_site -> string

branch_site_to_line ?source s is one stderr line naming s: its source line (and column), the branch, the instruction before it, and, given the source the listing was compiled from, that line's text.

val explain_branch_claim : ?out:??? -> ?source:??? -> prefix:string -> holds:Base.bool -> branch_site Base.List.t -> Base.bool

explain_branch_claim ?out ?source ~prefix ~holds sites is holds, and when it is false prints every site of sites -- each conditional branch with the instruction before it and its source line (branch_site_to_line) -- to out (stderr by default), one line each behind prefix and tagged (not part of the golden). A claim that holds prints nothing, so a golden cannot depend on what a compiler emitted around it.

GPU machine code (gh-ocannl-1695)

The branch question of conditional_branch_sites, asked of a GPU kernel the backend compiled. The device compilers are in-process libraries (NVRTC, HIPRTC) whose options a test cannot reach, so nothing is re-compiled: the census reads the code object the run produced, which its debug-artifact compile carries line tables for (Compiler_options.nvrtc's and hiprtc's ?with_line_info).

  • CUDA: the run's <routine>.ptx, assembled for the .target it names by the toolkit's ptxas (the driver's JIT does the same at load; the toolkit's version is the reading's provenance), then nvdisasm -g -c: SASS, each instruction under a //## File "<file>", line <n> marker.
  • HIP: the run's <routine>.hsaco, through llvm-objdump -d -l, each instruction under a ; <path>:<n> marker.

A CONDITIONAL branch is a BRA / BRX / JMP / JMX whose guard predicate is not the always-true PT (a predicated load or arithmetic instruction is not one: that is what an if-converted select looks like), and any AMDGPU s_cbranch_* -- the exec-mask skip around a divergent region included, which is how AMDGPU spells a branch around a load. Loop control is NOT exempted: no GPU dump has yet shown it attributed to a select's line, and a form no fixture pins would be filtered unexplained.
