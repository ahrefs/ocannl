Module Verdict

Test verdicts that cannot be dune promoted into passing (gh-ocannl-601).

A (test) stanza gates a run on two things: the executable's exit status, and the diff between its stdout and the .expected golden. A test that decides its own verdict — printing "PASS", "FAIL: …" or "<claim>: false" — and exits 0 regardless has only the second gate, and the second gate is promotable. A genuine failure changes stdout, the diff fails, and the natural next move — dune promote — records the failure text as the expected output. Nothing fails again until someone reads the golden, and in a golden that is nothing but verdict lines a blessed failure is indistinguishable from a designed one: the boolean form is the worst of it, since a promoted false reads exactly like an intentionally recorded negative fact.

So verdicts go through here. Each check records its outcome; a run with any failure exits nonzero from a teardown registered once, whatever the checks are and however many of them there are — so a test built on this module gets the exit-status gate by construction, without an end-of-file call it could forget. The failures are also echoed to stderr, because dune neither displays nor diffs the redirected stdout of a process that exits nonzero: it does write it, to <name>.exe.output (or the rule's .actual) under _build/default/<dir>/, where tools/mutation-run.sh reads it, but stderr is the channel on which the message reaches whoever ran the build.

Assertions belong here; descriptive output does not. Printing a fact the golden pins ("losses: 1.0; 0.5", "producer inlined: true" where the point is to record what happened) stays a plain printf. What comes here is the line whose content IS the pass/fail decision.

val claim : Base.string -> bool -> Base.unit

claim name b fails the run when b is false, printing nothing on stdout: for a test that renders the boolean itself, in a column layout of its own. Prefer p, which does both.

val p : Base.String.t -> bool -> Base.unit

p name b prints the named boolean fact name: b and fails the run when b is false. Booleans keep .expected files backend-stable, which is why so many tests report this way; a fact whose expected value is false should be renamed to the claim that holds, so that every line of a golden reads as an assertion that passed.

val pf : ('a, unit, string, bool -> Base.unit) Stdlib.format4 -> 'a

pf fmt … b is p with a COMPUTED label: the format and its arguments render the label, and the boolean follows, so the call reads in the same order as p name b — Verdict.pf "%s gradients match the oracle" label ok prints "… gradients match the oracle: true" and fails the run on false.

This is the entry point for the claims gh-ocannl-601 could not convert (gh-ocannl-624): a claim whose label names which leg, which epoch or which measured quantity it is about has to build that label from an argument, and before this it had no choice but a bare printf — which exits 0 on false and lets the failure be dune promoted into the golden, the exact hazard the literal-label sites were swept for. A computed label is not a weaker claim than a literal one, so it must not have a weaker gate.

The rendered label is what p prints and what a failure names on stderr, so it should read as the fact that holds — the same rule as p: phrase it so true is the passing reading.

val claimf : ('a, unit, string, bool -> Base.unit) Stdlib.format4 -> 'a

claimf fmt … b is claim with a computed label: it fails the run without printing anything on stdout, for a test that renders the boolean itself in a column layout of its own. Prefer pf, which does both; reach for this only where the surrounding line is a table whose shape is the point, and bind the boolean to a name used by both the print and the claim, so the two cannot drift apart.

Quantified claims

"every X …" is TRUE of an empty X, and in a golden that line is byte-identical to one a real population passed (gh-ocannl-729). The hole is invisible by construction, and it opens exactly where the claim is most worth making: quantified over a DERIVED collection — the seeds a family tree yields, the refutations a gate raises, the statements a kernel emits — where the collection being empty is a plausible regression rather than an impossible one. A seeding change that empties a family silently converts several claims from checks into decoration.

So a quantified claim goes through one of the combinators below rather than through p applied to a List.for_all: they carry the non-emptiness guard, which makes the guarded form the shortest one to write. A non-empty collection prints exactly what p prints, so goldens keep their shape; an empty one prints a DISTINCT <claim> (empty): false, so a reader sees why the line failed without opening the source.

The single-collection combinators take lists; an array reaches them through Array.to_list, which is free at test scale and keeps this library's surface small. The PAIRWISE one, p_all2, is the exception and takes arrays — the executed-parity genre it serves reads both sides out of Context.get_values, and it has to compare their LENGTHS, which is the one question a list cannot answer without walking it.

?min raises the floor for a site that knows one — "every one of the four curated tiles …" is a different claim from "every tile …", and a menu that silently shrank to one member should fail it. In p_all, p_none and p_empty it bounds the COLLECTION, which is where those claims can go vacuous; in p_exists it counts WITNESSES, for the reason given there. Below the floor the line names the shortfall: <claim> (only 1 of 4): false. The floor only RAISES: a ?min below 1 is an Invalid_argument wherever a combinator taking one is evaluated, because ~min:0 reads as "emptiness passes" and no floor can grant that -- a vacuous quantifier is refused by design (gh-ocannl-729). A claim whose passing case is emptiness says so with p_empty, whose ~over names the population that must exist, or -- where nothing in scope must be non-empty -- with p over the unguarded quantifier and the reason said at the site, which is what the ratchet's exemption list keys on.

type all2_outcome =
  1. | All2_short of Base.string
  2. | All2_holds of {
    1. failed : Base.int;
    2. first : Base.int;
    }

p_all2 name got want ~f claims that got and want agree cell for cell under f, that they have the same length, and that there is a cell — the guarded form of p name (Array.for_all2_exn got want ~f), and the executed-parity genre's entry point (gh-ocannl-746). Reach for it wherever a claim compares a readback against a reference.

Emptiness is not far-fetched here, which is why the guard matters more than it looks. Both sides usually come from Context.get_values, and a node that stopped being materialized, a reference run whose own setup collapsed, or a readback of a virtualized node answers with NOTHING ON BOTH SIDES AT ONCE — the reference does not discriminate, because it went through the same path. Array.for_all2_exn [||] [||] is true, so the line that reports the strongest kind of check AGENTS.md asks for is byte-identical to one a real readback passed.

A LENGTH MISMATCH is reported as a failed claim, <claim> (length 12 vs 16): false, rather than as the Invalid_argument Array.for_all2_exn raises: an exception fails the run too, but it fails it without a claim line and without naming which claim, and the mismatch is a finding about the run (one side was reshaped, or one readback was truncated) that deserves to be read off the transcript. Reported before emptiness, so a one-sided empty says which side it was.

?min bounds the COMMON length, as in p_all.

A VALUE failure prints the bare <claim>: false p prints, and adds one line on stderr, which no golden diffs: how many cells failed f and the first of them, <claim>: 2 of 64 cells fail the predicate; first at 17 (not part of the golden) (gh-ocannl-1224). f therefore runs on every cell once the population floor is met, as in p_all. It cannot print the values, since it does not know their type: a claim over float readbacks under a tolerance goes through p_close, which does.

Float parity under a tolerance (gh-ocannl-1224)

p_close name got want ~tol claims that the float readback got matches the reference want cell for cell: each got.(i) equals want.(i), or lies within tol want.(i) of it (Float.(abs (got - want) <= tol want)). tol answers the admitted difference for a reference value, so one argument spells every tolerance the parity tests use: absolute (fun _ -> 1e-3), relative with an absolute floor (fun w -> 1e-3 +. (1e-5 *. Float.abs w)), relative above magnitude one (fun w -> 1e-4 *. Float.max 1. (Float.abs w)), or exact (fun _ -> 0.). Its structural refusals are p_all2's -- an empty pair, a length mismatch, a pair below ?min -- and so is its passing line.

What it adds is the failure: the bare <claim>: false on stdout, as p prints it, and on stderr one line that answers the triage questions a bare false cannot, outside every golden: <claim> (<what_ran>): 3 of 4096 cells differ beyond tolerance; first at 17, worst at 902: got 196608.031 vs want 196608 (|diff| 0.0312, tolerance 0.001 there); max |want| 2.1e+05 (not part of the golden). The worst cell is the failing one furthest from its reference (a NaN on either side ranks first), and max |want| is the magnitude that tells a few ulps of reordered rounding from a misread operand at a glance. gh-ocannl-1217 needed a reproduction round on a remote box to learn exactly that; with this line, the sweep log alone carries it. ?what_ran names the candidate that produced got (a seed, a schedule, a preset) when the label is shared across a loop of them.

~difference_only:true preserves a legacy abs-of-difference comparison exactly, without the equality shortcut or finite-difference requirement. This lets migrated error-fold claims retain their treatment of infinities and unusual tolerances while sharing the same diagnostics.

By default, a cell where the two values are EQUAL holds whatever tol says, so matching infinities match, and a NaN on either side never does. The bound is inclusive, so fun _ -> 0. is exact equality.

val within : ?min:??? -> ?what_ran:??? -> ?difference_only:??? -> Base.String.t -> Base__Float.t Base.Array.t -> Base__Float.t Base.Array.t -> tol:(Base__Float.t -> Base.Float.t) -> bool

within name got want ~tol answers whether p_close would pass, WITHOUT making a claim: on a false it prints p_close's stderr line (or the structural reason, <name>: empty (not part of the golden)) and records nothing. It is the predicate of an aggregate claim over candidates whose number is not the golden's to pin -- p_all "every seed matches" runs ~f:(fun (seed, got) -> Verdict.within ~what_ran:seed "the block" got want ~tol) -- so that the claim stays one row while the candidate that failed it still names its worst cell. ~difference_only:true is p_close's compatibility mode, also used by Ll_test.close. val p_none : ?min:??? -> Base.String.t -> 'a Base.List.t -> f:('a -> Base.bool) -> Base.unit

p_none name xs ~f claims that no element of xs satisfies f, and that there is an element — the guarded form of p name (not (List.exists xs ~f)) and of p name (List.is_empty (List.filter xs ~f)). The mirror of p_all, and the one the "no X is …" claims want: filtering an empty collection also yields nothing, so the unguarded spelling passes on an empty input just as List.for_all does.

val p_alli : ?min:??? -> Base.String.t -> 'a Base.List.t -> f:(int -> 'a -> Base.bool) -> Base.unit

p_alli name xs ~f is p_all with each element's index beside it -- the guarded form of p name (List.for_alli xs ~f), for the claims that compare an element with its neighbour or with a reference at the same position. Arrays go through Array.to_list, as for p_all. Like p_all, it evaluates every element once the population floor is met.

val p_empty : ?min:??? -> Base.String.t -> over:'a Base.List.t -> 'b Base.List.t -> Base.unit

p_empty name ~over xs claims that the derived collection xs is empty, and that the collection it was derived from, over, is not — the guarded form of p name (List.is_empty xs) where xs is a precomputed subset (the invalid seeds, the declined candidates, the offending rows) of a population that must itself exist. Prefer p_none where the predicate can simply be passed; this is for the sites that keep the derived list around to report it.

val p_exists : ?min:??? -> Base.String.t -> 'a Base.List.t -> f:('a -> bool) -> Base.unit

p_exists name xs ~f claims that some element of xs satisfies f, and p_exists ~min:n that at least n do. Its ?min counts WITNESSES where its siblings' counts the population, and the asymmetry is the point rather than an inconsistency: for an existential a population floor buys nothing, since List.exists already answers false on an empty collection, so the only reading of ~min:2 that adds a constraint is "two of them". Reading it as a population floor is what would produce the false green this module exists to prevent — a two-element list with one witness passing "at least two of the seeds pipeline" (Codex P2, round 1).

An empty collection still says so: <claim> (empty): false, because "nothing satisfied f" and "there was nothing to satisfy it" are different findings. Too few witnesses under an explicit floor names the shortfall as <claim> (only 1 of 2 match): false — "match", so that the line cannot be read as the population shortfall its siblings print. At the default floor of one the line is the bare <claim>: false p would print: there is no shortfall to name.

val p_pairwise_distinct : Base.String.t -> 'a Base.List.t -> equal:('a -> 'a -> bool) -> to_string:('a -> string) -> Base.unit

p_pairwise_distinct name xs ~equal ~to_string claims that xs contains at least two elements and that no two of them are equal. It reports the first colliding pair in source order directly: <claim> (collision: x = y): false. to_string is evaluated only on a collision, so a passing claim pays only for the comparisons and keeps the same stdout line as p.

This is the guarded form of building every unordered pair and passing it to p_none. The source-population floor belongs here rather than on the derived pairs: zero source elements produce zero pairs, but one source element does too, and neither is evidence of distinctness (gh-ocannl-815).

Who executes a claim the fleet sweep cannot (gh-ocannl-926): the `Outside_sweep scope's owner, written into the skip record so that ownership is a fact the tree is checked against rather than a comment. test/operations/sweep_owner_scan resolves every owner spelled in the tree, and refuses the scan when the matrix it names is gone.

  • Ci_step { workflow; step; alias }: the step named step of .github/workflows/<workflow> builds @<alias>, and <alias> is the per-test alias of the stanza that compiles the skipping source -- the compiler-trace CI leg owning cc_backend_trace_name's level-3 claim.
  • Plain_run { alias; forcing }: the skip occurs only when the command line carries the atom forcing, and @<alias> -- a stanza compiling the same source and passing no forcing -- runs the claim on the sweep itself: cache_key_agreement's -outranked rule, owned by the plain run, and cuda_wmma_floor's forced missing-toolkit arm, owned by the real witness.

type skip_aggregation = [
  1. | `Backend
  2. | `Environment
  3. | `Outside_sweep of sweep_owner
]

skipped ~backend name reports a leg the run's backend cannot evaluate: a GPU intrinsic on a CPU backend, a tf32 policy outside CUDA. It prints the same stdout line p would — the .expected goldens are backend-uniform, and a (test) stanza diffs stdout ONLY, so stderr is free — and announces the skip on stderr, naming the claim. grep SKIPPED over a run then enumerates exactly what that hardware did not verify. A second OCANNL_TOOL_VERDICT_SKIP<TAB>scope<TAB>executable<TAB>claim record on stderr (an outside-sweep one ends in a fourth <TAB>owner field) is the machine-readable form, and the one the action's record file receives (the per-action records above), which is what the forced sweep intersects across backends; the executable identity keeps equal labels in different test legs distinct there. scope is backend by default. Pass ~aggregation:`Environment when the leg is gated by a host or configuration capability rather than the selected backend, such as a compiler target, preprocessing flag or filesystem feature; its human announcement remains visible, and the forced fleet sweep aggregates it across the measurement boxes declared by benchmarks/fixtures/DIGESTS.txt instead of mistaking it for unsupported backend coverage. Scope describes this observation, not the claim identity: if any declared-box log marks a claim Environment, a Backend skip carrying the same executable and claim key on another box is also evidence that box did not execute it. Pass ~aggregation:(`Outside_sweep owner) only when another checked run owns execution of the claim, and name it (sweep_owner): the compiler-trace CI leg, or the plain run of an executable a rule forces into the skip. The record carries the owner as a fourth field (sweep_owner_field) and remains validated and human-visible, but neither sweep dimension treats its absence as evidence; test/operations/sweep_owner_scan fails when the owner no longer resolves, so deleting the matrix is a red rather than a silent loss of coverage. An owner the record grammar cannot carry is a failed check.

Use it in place of a bare p name true: that line is byte-identical to a verified run's, so neither the transcript nor a reviewer can tell the claim was never evaluated — which is how a Tensorize leg came to "cover" the gh-ocannl-528 interior-batch bug without ever checking it. A gate folded into the claim's value, p name ((not gate) || b), prints that same line where the gate is closed, and verdict_ratchet refuses it (gh-ocannl-1310). The other honest form is putting the condition into the label itself ("… (skipped: non-C backend)"), which distinguishes the golden line; only the indistinguishable bare true is the one to reject.

~backend is the run's backend name, as each test already derives it for its own gating (String.lowercase (Utils.get_global_arg ~arg_name:"backend" ~default:"")). It is passed in rather than read here so that this library keeps depending on no OCANNL library, only base, stdio and unix: reporting a verdict is not a reason to link OCANNL's configuration machinery.

Hatched claims: a third state between a pass and a skip (gh-ocannl-996)

Some claims executed and still cannot be judged on this run: a timing envelope over a window the instrument itself declared contended, a recording that clean evidence never allowed. Their escape -- the HATCH -- is correct, since a stalled window cannot be held to a bound. Written as a disjunct of the claim's value, p "…" (reading.contended || within_envelope), it is also silent: the claim prints true and records an evaluation whether or not it was checked, so a unit where it is bypassed in seven runs out of eight reads exactly like one where it is verified every time. gh-ocannl-994's defect hid that way for weeks.

p_unless ~unless:[ (hatch, taken); … ] label b takes the hatch as its own argument. Where no hatch is taken it is p over b (or, with ?detail, gated's rendering of a failure), and it writes OCANNL_TOOL_VERDICT_CHECKED<TAB>hatches<TAB>executable<TAB>claim to the action's record file, naming every hatch it declares. Where one is taken, b is not judged: it prints the same label: true row a check prints, so the golden is the same either way, and reports BYPASSED (<hatches taken>): <label> on stderr with the machine record OCANNL_TOOL_VERDICT_BYPASS<TAB>hatches<TAB>executable<TAB>claim beside it, which the record file receives too. No EVALUATED record is written for a bypass. A claim's two records are the numerator and denominator of its BYPASS RATE, which the sweep reports per unit (tools/aggregate-bypasses.sh); a run whose every hatched claim was bypassed carries BYPASS records and no CHECKED one, where a fully checked run carries the reverse.

A hatch is a RUN-TIME condition the instrument reports about this very run (the window was contended, the evidence was unclean); a capability of the backend or host is a gate, reported through gated, whose closed side is a skip. Every occurrence is recorded -- unlike EVALUATED, once per label -- because a claim reached several times in one action is several chances to be checked. unless must name at least one hatch: an empty list is a failed check, since it is a plain p that would record a denominator for a claim with nothing to bypass.

val maybe_hatched : ?unless:??? -> Base.String.t -> (unit -> Base.unit) -> Base.unit
val measure : string -> (string * string) Base.List.t -> unit

measure name fields records what an instrument measured on this run, as OCANNL_TOOL_VERDICT_MEASURE<TAB>executable<TAB>name<TAB>key=value…, on stderr and in the action's record file: the numbers a bound's health depends on (a timing window's depth, minimum, median, mean, its contention flag), kept where the sweep collects records, so that the next threshold question is a query over the fleet's nights rather than a campaign that drives the executable and parses its human stderr (gh-ocannl-996). It claims nothing and prints nothing on stdout. Keys and values are escaped onto one line; a key should carry no =, since the first one in a field is where a reader splits it.

val gate : ?aggregation:??? -> when_:bool -> on:Base.String.t -> Base.String.t -> (unit -> Base.unit) -> Base.unit
val gated : ?aggregation:??? -> ?detail:??? -> ?unless:??? -> when_:bool -> on:Base.String.t -> Base.String.t -> Base.bool -> Base.unit

gated ~when_ ~on label b is a claim that is evaluated only where the gate when_ is open: there it is p — label: true, or a failure — and where the gate is closed it is skipped ~backend:on, b unread. Both outcomes print label: true on a passing run, so a host that legitimately skips cannot break the .expected golden (gh-ocannl-997).

It exists because that byte-identity was a convention the call site had to know. A gated claim written as if gate then pass_fail label b else skipped ~backend label records label: PASS in the golden on the machine that promotes it, and fails the diff with label: true on the one machine that reaches the skipping regime — which is the machine least likely to be promoting. Twice this shipped as far as review (staging#735's depth gate, and a host gate in gh-ocannl-1031's first draft). This entry point picks the dialect itself, and verdict_ratchet refuses a label that reaches both pass_fail and skipped.

~on names what the run was on when it skipped — a backend for the default `Backend aggregation, a host or configuration capability for `Environment — and is printed as SKIPPED on <on> (vacuous): <label>. It is ~on rather than skipped's ~backend because a host gate is not a backend. ?aggregation is skipped's.

?detail is what pass_fail offered and a gated claim had to give up: evaluated only on an evaluated failure, and rendered the way this dialect renders what a bare false cannot say, <label> (<detail>): false — the place for a measured number that must stay out of a passing golden.

b is an ordinary bool, evaluated by the caller whatever the gate says, so it must be computable off-gate — which is also what lets verdict_ratchet's quantifier reader treat this exactly as p. A claim that cannot even compute its boolean without the gate goes through a leg (in_leg), which evaluates it on one side and skips it on the other in the same dialect. A quantified claim goes through gated_all and its siblings.

?unless makes the claim a hatched one (p_unless) where the gate is open: the gate is judged first, so a closed gate is a skip whatever the hatches say, and only a claim this run would evaluate can be bypassed.

val gated_all : ?aggregation:??? -> ?min:??? -> ?unless:??? -> when_:bool -> on:Base.String.t -> Base.String.t -> 'a Base.List.t -> f:('a -> Base.bool) -> Base.unit

gated_all ~when_ ~on label xs ~f is gated for a quantified claim: p_all where the gate is open, skipped ~on where it is closed. gated_alli and gated_exists do the same for p_alli and p_exists, and ?min, ?aggregation and ?unless mean what they mean there.

gated cannot carry these: gated label (List.for_all xs ~f) is the unguarded quantifier verdict_ratchet refuses in p too, since a gate does not fill the population. Without this family the guarded spelling was a hand-written branch, if gate then p_alli label xs ~f else skipped ~backend label, repeating the label and the skip's arguments at every site.

Where the gate is closed, neither xs nor f is read. A leg whose population exists only where it ran (the seeds a GPU proposes, the files a host could create) can therefore pass the empty list it is left with off-gate, computed unconditionally; the non-emptiness floor applies exactly where the claim is evaluated -- and so does the refusal of a ?min below 1, since a floor computed from that same population (~min:(List.length xs)) is zero exactly where the gate is closed. A leg whose population cannot be computed off-gate at all (a device readback) goes through a leg, as gated says of its boolean.

val pass_fail : ?detail:??? -> Base.string -> bool -> Base.unit

pass_fail label b prints label: PASS or label: FAIL, and fails the run in the latter case, echoing that row behind FAIL: on stderr. ?detail is evaluated only on failure and appended in parentheses — the place for a machine- specific number (a measured value, a difference) that must stay out of a passing golden.

Not for a claim some host skips: skipped prints label: true, never label: PASS, so that pairing breaks the golden wherever the skip fires. A gated claim goes through gated.

Legs: one claim sequence on both sides of a gate (gh-ocannl-1703)

A test whose evidence exists only on some backends -- a GPU compile, a CPU pool, a host's fork -- used to be written as two branches: the evaluating one, making its claims with their labels, and the other skipping a hand-written list of the same labels. Since the golden is backend-uniform, that list IS the golden's order off the gate, and it is a second copy of the first branch's labels that nothing ties to the first: grid_launch_floor had two claims appended to its list's end while the evaluating branch made them mid-sequence, which reddened Metal, CUDA and HIP on the integration loop (gh-ocannl-1668), and dozens of tests carried the same drift risk.

A leg removes the second copy. The claims are written ONCE, as in_leg ~leg label make, in the code that runs on every backend: where the leg is open, make label evaluates the claim; where it is closed, the claim is skipped under the same label, in the order the same code reaches it. A renamed, reordered or inserted claim moves both sides at once, because there is only one side. Evidence the closed side cannot compute goes in a lazy that only the make functions force, so nothing gated runs off the gate: let small = lazy (run ~n:32 ...) in then in_leg ~leg "..." (fun label -> p label (holds (Lazy.force small))).

make receives the label so that it cannot restate it, and its evaluation is held to exactly that: one claim recorded, under label, printed as a <label>: <bool> row -- through p, a quantified or parity combinator, gated or a nested skipped. Anything else is a failed check naming the leg claim, since the closed side prints <label>: true and a make that claimed under another label, printed PASS/FAIL (pass_fail), printed nothing (claim) or made two claims would break the golden exactly where the leg is closed -- the machine least likely to be promoting it.

leg ~when_ ~on () is a leg open where when_ holds and closed elsewhere, skipping as SKIPPED on <on>; ~on and ?aggregation mean what they mean for gated. when_ is a gate: the backend, an advertised capability, the configuration -- never the values under test.

val sub_leg : ?aggregation:??? -> leg -> when_:bool Base.Lazy.t -> on:Base.string -> leg

sub_leg outer ~when_ ~on is open where outer is open and when_ then holds: for a gate the evaluating side alone can compute (a capability its device reports, a geometry its compile chose). when_ is forced only where outer is open; where outer is closed, its claims skip as outer's do, and where when_ is false, as SKIPPED on <on>.

val in_leg : leg:leg_state Base.Lazy.t -> Base.String.t -> (Base.String.t -> unit) -> Base.unit

in_leg ~leg label make is make label where leg is open, held to making exactly the one <label>: <bool> claim, and skipped label where it is closed (see above). If the run itself makes claims (for example a test helper that checks execution), run it ahead of the in_leg calls, under the leg's own gate, as mixed_prec_twin_rounding's run_placements does, and pass its result in. The run's own claims must print no golden row or must themselves be leg claims, so the closed side retains the same golden rows. Extra claims inside make violate this one-claim boundary.

val case : Base.String.t -> (unit -> unit) -> unit

case label f runs one case of a test -- a group of claims that share a setup -- and turns an exception escaping it into a failed claim, <label>: the case ran to completion (raised <exception>): false, so that the cases after it still run (gh-ocannl-1067). It prints nothing of its own when f returns, so wrapping a case is golden-neutral.

Without it an exception ends the run at the case that raised. The teardown then says so (STOPPED EARLY on stderr, and the exception itself), but the rows after that case are never evaluated: a negative control that made one case raise learns nothing about the others. With it, each case is its own verdict, which is what a test of many independent rows wants.

The exception's text goes on the claim line (echoed to stderr like every failure), and the backtrace, when one is recorded, to stderr. What an explicit exit raises is let through, not recorded: that is the process ending, not a case failing. Once a check has failed, that ending is reported as STOPPED EARLY: an exit inside case "<label>" … on stderr (gh-ocannl-1084): a run that ended inside a case never ran the cases after it, and a reader counting rows (tools/mutation-run.sh) cannot otherwise tell it from a run whose earlier case raised and whose later ones completed.

val success_trailer : ?blank_line:??? -> Base.String.t Base.List.t -> unit

success_trailer ?blank_line rows prints each of rows as an OK: <row> line, behind an empty line when blank_line, provided no check has failed so far -- and nothing otherwise: a scan's closing statement of what its claims established, which a failing run must not print. It is the one shape a success trailer takes. tools/mutation-run.sh matches a failing run of a scan against its golden without the trailer's OK: rows and the empty line before them, and tools/test-mutation-run.sh replays verdict_teardown's transcripts of runs that print through here, so a trailer reworded here turns that harness red instead of the runner reading every failing run of every scan as stopped early (gh-ocannl-1364). Each row prints on one line (one_line).

val exit_negative_control : unit -> 'a

Ends a NEGATIVE-CONTROL run, one whose failures are the output its golden pins: exits 1 when something failed and 0 when nothing did, without the teardown's "FAILED: n checks …" line. That line totals the failure lines above it, and a total in a golden merges wrong -- two branches each adding a control merge the lines right and the count wrong (gh-ocannl-1056). The rule running such a control accepts exit 1 alone, so a control that stopped refusing still fails.
